# US-040: Ripristinare la compilabilità della build release

**Epica:** EP-001 | **Punti:** 2 | **Branch:** `fix/US-040-release-build`
**Piano redatto:** 2026-08-06

## Contesto

`flutter build apk --release` fallisce:

```
Execution failed for task ':isar_flutter_libs:verifyReleaseResources'
AAPT: error: resource android:attr/lStar not found
```

**Causa accertata.** Il pacchetto `isar_flutter_libs-3.1.0+1` dichiara nel proprio `android/build.gradle`:

```groovy
compileSdkVersion 30
```

L'attributo `android:attr/lStar` è stato introdotto con **API 31**. Le dipendenze AndroidX moderne, tirate dentro transitivamente dagli altri plugin dell'app, lo referenziano. Quando AGP verifica le risorse del modulo `isar_flutter_libs` — compilato con SDK 30 — non trova l'attributo e si ferma.

Perché solo in release: il task `verifyReleaseResources` esiste solo per quel tipo di build. In debug la verifica non viene eseguita, quindi il difetto è rimasto invisibile.

Perché non è mai emerso prima: l'ultimo `app-release.apk` presente sul disco è datato **28 gennaio 2026**. Da allora nessuno ha provato una build release, e Isar è stato introdotto dopo.

## Obiettivo

Rendere di nuovo possibile produrre un pacchetto di release installabile.

## Approccio

Alzare il `compileSdk` dei sottoprogetti che ne dichiarano uno inferiore a 31, agendo nel `build.gradle.kts` di root con un blocco `afterEvaluate`.

Alzare il `compileSdk` di un modulo **non ne cambia il comportamento a runtime**: `minSdk` resta quello dichiarato dal pacchetto, e con esso la compatibilità con i dispositivi vecchi. Cambia solo la piattaforma con cui il codice viene compilato, che è esattamente ciò che serve perché `lStar` venga risolto.

L'intervento è mirato: tocca solo i moduli sotto la soglia, quindi se un aggiornamento futuro di Isar alzasse il proprio `compileSdk`, il blocco diventerebbe inerte da solo invece di forzare un valore.

### Alternative scartate

| Alternativa | Perché no |
|---|---|
| Forzare `androidx.core` a 1.6.0, che non usa `lStar` | Retrocede una dipendenza che altri plugin richiedono più recente: si sposta il problema invece di risolverlo |
| Aggiornare Isar a una versione con `compileSdk` più alto | Isar 3 non riceve aggiornamenti; Isar 4 non è stabile. La sostituzione è discussa in EP-008 |
| Sostituire Isar adesso | Intervento grosso, intrecciato con US-002 e US-003 in EP-008. Qui serve solo tornare a produrre un pacchetto |
| Disattivare `verifyReleaseResources` | Nasconde l'errore invece di correggerlo: un problema di risorse reale non verrebbe più segnalato |
| Fissare `compileSdk` a un valore alto su tutti i sottoprogetti | Forzerebbe anche i moduli già a posto, e resterebbe a forzarli per sempre |

## Passi

1. Aggiungere il blocco ai sottoprogetti nel `build.gradle.kts` di root.
2. `flutter clean` per evitare che risorse già verificate mascherino l'esito.
3. `flutter build apk --release --split-per-abi`.
4. Verificare che la build debug continui a funzionare.
5. `flutter analyze` e `flutter test`.
6. Riportare la dimensione del pacchetto ottenuto.

## Piano di test

| Criterio di accettazione | Come lo verifico |
|---|---|
| `flutter build apk --release` termina con exit code 0 | Esecuzione dopo `flutter clean` |
| Il pacchetto si installa e si avvia su un telefono reale | **Da confermare sull'APK**: non ho un dispositivo collegato |
| `flutter build apk --debug` continua a funzionare | Esecuzione esplicita dopo la correzione |
| La causa è documentata nel file toccato | Commento nel `build.gradle.kts` con diagnosi e condizioni di rimozione |
| La dimensione del pacchetto è riportata | Misura dopo la build |

## Rischi

| Rischio | Come me ne accorgo | Mitigazione |
|---|---|---|
| Alzare `compileSdk` rompe un altro plugin | Errore di compilazione su un modulo diverso | La build stessa è la verifica; il blocco tocca solo chi è sotto la soglia |
| Il blocco resta anche quando non serve più | Nessun segnale | Condizionale sulla soglia: diventa inerte da sé. Il commento spiega quando rimuoverlo |
| Firma con chiave di debug | La release è firmata con la chiave di debug, come dichiarato nel `TODO` di `app/build.gradle.kts` | Va bene per le prove interne; una chiave vera serve solo per la distribuzione sugli store, che non è in programma |
| Comportamento a runtime alterato | Regressione sul dispositivo | `minSdk` non viene toccato: cambia solo la piattaforma di compilazione |

## Fuori scope

- Configurare una chiave di firma di produzione: non serve per le prove interne
- Sostituire Isar: è EP-008
- Ridurre la dimensione del pacchetto oltre a quanto fa `--split-per-abi`
- Automatizzare la build release nella CI
